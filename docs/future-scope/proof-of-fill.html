Idea name

Proof-of-Fill

One-line pitch

An evidence board that lets holders of tokenized real-world assets verify the off-chain broker fill behind every mint — by opening the commitment the settlement contract already published.

Which track?

C — DeFi (Marcos · 21–31 Aug)

Form · page 1 The problem — and who it's for Long text, required.

A hash nobody can open

Paste-ready · 787 / 800

Tokenized equity and RWA protocols settle on-chain but execute off-chain at a regulated broker. When a fill returns, the backend computes a salted keccak256 commitment over it — order id, price, USDC settled, oracle price, salt — and emits the hash in OrderSettled. The hash is permanent and public; the preimage, salt included, sits in one 0600 JSON file on the operator's disk. So the holder gets a bytes32 they can never open: the issuer can withhold it, reveal it selectively, or lose it forever. Unlike a DEX, a broker's fill has no mempool or public print to check against. It's for holders who take "fair fill" on faith, and auditors who must price an issuer's trustworthiness.

Writeup: https://docs.google.com/document/d/1p-xaD5QuHtNRY21AvHJF7Kff322UsjdTBtgsGTtcGok/edit?tab=t.0

Longer reasoning — reference, not for the 800-char field

Concretely, in the settlement path I built: when a fill returns from the broker, the backend computes a salted commitment — keccak256 over the order id, symbol, receipt units minted, fill price, USDC settled, the oracle benchmark price, its publish time, and a random salt — and the contract emits it in its OrderSettled event. The hash is permanent and public. The preimage, salt included, is written to one JSON file at mode 0600 on the operator's own disk.

So the holder ends up with a bytes32 they can never open. Nothing obliges the issuer to publish the preimage, nothing stops them revealing it to one holder and not another, and if that file is lost the commitment is unopenable forever — the salt makes brute force infeasible. What makes this different from a DEX is the counterparty: a solver's fill is observable and anyone can replay the chain to catch a bad one, but a broker's fill has no mempool, no public print, no block to compare against. The only account is the issuer's, and the only check on it is a hash whose preimage the issuer keeps.

Form · data model Entities & typed attributes Where the rubric scores hardest — 20 points.

Six entity types, linked by orderId

Paste-ready · 1140 / 1200
Six entity types, all tagged app="proof-of-fill" and linked by a shared orderId key (Arkiv has no joins — relationships are shared attributes). Integers wherever I need range filters; strings are eq-only. IntentCommitment (written pre-execution; payload = commitment + ciphertext hash, no plaintext) — str: orderId, symbol, side, requester, venueId; int: chainId, committedAt, requestBlock. ExecutionProof (the preimage of the on-chain commitment) — str: orderId, symbol, requester, deviationSide (worse/better/equal); int: filledAt, epochMonth, fillPriceUsdc, benchmarkPriceUsdc, absDeviationBps, unitsMinted, settledUsdcBase, qualityTier (0-3). BenchmarkSnapshot (oracle reference, one per round) — str: symbol, feedId; int: publishTime, priceUsdc, confBps. ReserveAttestation — str: symbol, attestor; int: epoch, attestedAt, brokerShareAtoms, unitsOutstanding, coverageRatioBps (10000=100%). DisputeClaim ($owner=holder) / DisputeResponse ($owner=issuer) — str: orderId, outcome; int: filedAt, claimedHarmUsdcBase. Prices are 6-decimal USDC base units, shares are atoms (1e9=1 share), deviation is bps — all integers so gt/lt work.

Every entity carries app="proof-of-fill" so filters stay selective in a shared public database. There are no joins — related entities share an orderId attribute and resolve with one equality filter.

Every numeric attribute below is an integer, because that is the only way to keep gt/lt available: prices in 6-decimal USDC base units, shares in atoms at 1e9 per share, deviations in basis points, timestamps in unix seconds. Anything I will only ever match exactly — symbol, side, wallet, venue, status — stays a string, since strings support eq only.

IntentCommitment expiresIn 15552000 · 180 d

Written when the sealed order reaches escrow, before execution. Payload is the intent commitment hash, the ciphertext hash and the request tx hash — never plaintext.

str attributes
kind="intent" · orderId · symbol · side · requester · venueId · settlementContract
int attributes
chainId · committedAt · requestBlock

Lifetime is pinned to the fill it precedes: if the intent expired first, the ordering check in Q5 would have nothing left to compare against.

ExecutionProof expiresIn 15552000 · 180 d

The preimage of the on-chain commitment, written once after settlement and never updated. Payload carries every field of the commitment tuple plus the salt, so any reader can recompute the hash themselves.

str attributes
kind="fill" · orderId · symbol · requester · venueId · deviationSide ("worse" | "better" | "equal")
int attributes
chainId · filledAt · epochMonth (202608) · fillPriceUsdc (6-dec base) · benchmarkPriceUsdc (6-dec base) · absDeviationBps · benchmarkAgeSec · unitsMinted · settledUsdcBase · qualityTier (0 ≤10bps, 1 ≤50, 2 ≤200, 3 >200)

Deviation is signed, and I need range queries on its magnitude — so the magnitude is a non-negative integer and the direction is a separate string matched with eq. Storing a signed value as text would have cost me the range query outright. 180 days is the window in which a holder can still contest a fill.

BenchmarkSnapshot expiresIn 2592000 · 30 d

The oracle reading used as the best-execution reference, written once per round rather than once per fill.

str attributes
kind="benchmark" · symbol · feedId · roundKey
int attributes
publishTime · priceUsdc · confBps

Deliberately shorter-lived than the proofs that reference it. Each ExecutionProof carries the benchmark values inline in its own payload, so this entity is a convenience index for "every fill priced off this round", not a source of truth. When it expires, verification still works — only the cross-fill grouping view degrades. That is the answer to what happens when a referenced entity lapses.

ReserveAttestation expiresIn 2678400 · 31 d, extended monthly

Per-epoch solvency disclosure for one symbol: what the broker actually holds against what the contract has minted.

str attributes
kind="reserve" · symbol · attestor
int attributes
epoch · attestedAt · brokerShareAtoms · unitsOutstanding · escrowUsdcBase · coverageRatioBps (10000 = 100%)

The one entity meant to be kept alive rather than left to lapse — see Lifetime Extension below. Its short lifetime is the mechanism, not housekeeping.

DisputeClaim expiresIn 1209600 · 14 d

A holder's challenge to a specific fill. $owner is the holder.

str attributes
kind="claim" · orderId · symbol · claimant
int attributes
filedAt · claimedFairPriceUsdc · claimedHarmUsdcBase

A claim is a short-lived request for an answer, so it lives 14 days and then lapses off the board.

DisputeResponse expiresIn 15552000 · 180 d

The issuer's answer, as a separate append-only entity. $owner is the issuer.

str attributes
kind="response" · orderId · claimKey · outcome ("upheld" | "rejected" | "remediated")
int attributes
respondedAt · remediationUsdcBase

Split from the claim on purpose. updateEntity is a full replace, so one shared mutable entity written by two adversarial parties would let either silently drop the other's attributes — and the read-then-write has a race. Append-only removes the shared writer entirely; status is derived client-side by joining on orderId, and a claim with no response past its window reads as lapsed. The response outlives the claim because it is part of the permanent record of the fill it concerns.

Five predicates the product lives on

Paste-ready · 909 / 1000
Q1 verify one fill: eq(kind,"fill") · eq(orderId,X) · limit(1). The client recomputes keccak256 over the payload, compares it to the on-chain OrderSettled commitment, and checks $creator == the issuer's settlement wallet. Q2 best-execution outliers: eq(kind,"fill") · eq(symbol,"TSLA") · eq(epochMonth,202608) · eq(deviationSide,"worse") · gt(absDeviationBps,50) — plus count() of all fills that month as the denominator ("3 of 412 were >50bps worse than benchmark"). Q3 worst-N, with no server-side ORDER BY: eq(qualityTier,3) narrows the set small enough to fetch whole, then sort client-side (results come back newest-first only). Q4 solvency: eq(kind,"reserve") · eq(symbol,X) · limit(1); a sweep lt(coverageRatioBps,10000) flags undercollateralization. An empty result = the attestation lapsed. Q5 ordering: confirm every fill has an IntentCommitment whose write preceded it — front-running evidence.

Q1 Open one commitment — the query the product exists for

eq(app,"proof-of-fill") · eq(kind,"fill") · eq(orderId,"tl-8f21…")
limit(1)

The client recomputes keccak256 over the returned payload, compares it with the executionCommitment read from the settlement chain, and checks $creator against the issuer's known settlement wallet. A hash that matches but a creator that doesn't is still a failure. Binary outcome, no interpretation.

Q2 Best-execution outlier report for one month

eq(kind,"fill") · eq(symbol,"TSLA") · eq(epochMonth,202608)
  · eq(deviationSide,"worse") · gt(absDeviationBps,50)

// denominator, as a count — not a fetch
count( eq(kind,"fill") · eq(symbol,"TSLA") · eq(epochMonth,202608) )

Renders as one sentence a holder can act on: 3 of 412 August TSLA fills came back more than 50 bps worse than the oracle benchmark. The count is what keeps this a dashboard query instead of pulling the whole month down.

Q3 Worst fills, without a server-side ORDER BY

eq(kind,"fill") · eq(symbol,"TSLA") · eq(qualityTier,3)
// then sort client-side on absDeviationBps

There is no server-side ordering, so limit-then-sort would return the top of a page rather than a true top N. Narrowing on qualityTier — a coarse integer bucket written at creation time — makes the candidate set small enough to fetch whole before sorting. That attribute exists for no other reason.

Q4 Live solvency — and its absence

eq(kind,"reserve") · eq(symbol,"TSLA") · limit(1)
// results are newest-first, the one ordering available and the one I need

// alert sweep across all symbols
eq(kind,"reserve") · lt(coverageRatioBps,10000)

If the first query returns nothing at all, the issuer stopped extending the attestation and the dashboard renders attestation lapsed. Absence is the signal — which only works because expiry is enforced by the protocol rather than by the issuer's cron.

Q5 Ordering check — front-running evidence

eq(kind,"intent") · eq(symbol,"TSLA") · gt(committedAt,T0) · lt(committedAt,T1)
eq(kind,"fill")   · eq(symbol,"TSLA") · gt(filledAt,T0)    · lt(filledAt,T1)

Join the two sets on orderId and confirm every fill has an intent whose Arkiv write landed before it. A fill with no prior intent, or an intent written after its own fill, is evidence the operator traded ahead of the order it was holding.

Form · data model Expiry, extension & ownership as product features Rubric wants these as mechanics, not checkboxes.

Three primitives doing product work

Paste-ready · 890 / 1000
Expiry: the 180-day contest window IS the ExecutionProof's lifetime, so the board is always exactly the set of fills someone can still challenge — no retention cron to trust. Lifetimes are differentiated by role: benchmarks 30d, dispute claims 14d, proofs and responses 180d. Extension: the ReserveAttestation lives 31 days and must be re-upped monthly. Renewal is an attributable act, and stopping is equally visible. On a plain DB a stale solvency claim just sits there looking current; here, going quiet makes the disclosure vanish and the dashboard renders "attestation lapsed." Silence becomes the signal. Ownership: immutable $creator is checked against the issuer's known settlement wallet, so a flattering proof published by anyone else fails verification. A DisputeClaim's $owner is the holder who filed it, so the accused issuer cannot edit it, delete it, or let it lapse early.

Entity Expiration — the contest window is the lifetime

A fill is challengeable for 180 days, then leaves the query surface. The board is therefore always exactly the set of fills someone can still act on, with no retention job to trust and no growing archive of stale evidence to wade through. Precisely: expiry removes an entity from the query surface, it does not erase on-chain history — so this is a bounded live board, not deletion, and I would not pitch it as a privacy erasure mechanism.

Lifetime Extension — a dead-man's switch for solvency

The ReserveAttestation is deliberately short-lived and must be re-upped every month. Renewal is an explicit, attributable act; stopping is equally visible. On a conventional database a stale solvency claim simply sits there looking current, and silence costs the issuer nothing. Here the default inverts: go quiet and the disclosure disappears, and the dashboard says so out loud. Silence becomes the disclosure.

$creator / $owner — the accused doesn't control the evidence

The audit view surfaces each proof's $creator next to the verdict, and a proof not created by the issuer's known settlement wallet fails verification even if the hash matches — that closes the obvious forgery, someone else publishing a flattering preimage. And a DisputeClaim's $owner is the holder who filed it, so the issuer cannot edit it, delete it, or let it lapse early. The board is the one place in this system the issuer cannot rewrite, which is the property everything else rests on.

What breaks on Postgres

Paste-ready · 684 / 700
On the issuer's own database the issuer is also the auth layer — it can backdate a proof, drop a dispute filed against it, or show one reader a different row. Three things then break: immutable $creator plus holder-owned dispute claims mean the accused can't rewrite the evidence; the front-running check needs "intent written before the fill," which an operator's created_at can't prove but a timestamped Arkiv write can; and the dead-man's-switch attestation only works if expiry is enforced by someone other than the party it embarrasses. Not on-chain either — event logs aren't filterable or countable by field, and permanent preimage storage is permanently costly and disclosing.
  1. The accused would own the evidence.

    On the issuer's own database the issuer is also the auth layer: they can backdate a proof, quietly drop a dispute filed against them, or serve one reader a different row. Immutable $creator plus holder-owned claims makes the board something the accused cannot rewrite. Without that, an issuer-hosted audit page is a nicer way of saying trust me.

  2. The ordering check needs timestamps I don't control.

    Q5's entire value is that the intent was committed before the fill. An operator's created_at is a column the operator writes; an Arkiv write is a transaction with a hash. Remove that and front-running detection isn't weaker, it's worthless.

  3. Expiry has to be a guarantee, not a cron job.

    The dead-man's switch only works if lapsing is enforced by something other than the party it embarrasses. A paused cron leaves a stale attestation reading as current solvency — the exact failure the mechanism exists to prevent.

  4. Publication becomes a precondition.

    Today the preimage's existence is entirely at the operator's discretion, and its absence is invisible. Writing it to a public queryable store means the audit trail either exists for everyone or visibly doesn't exist at all — and the gap between the on-chain settlement count and the proof-entity count is itself a published number.

And why not simply on-chain

Event logs aren't filterable, countable or paginable by field, so Q2 and Q3 are impossible without a private indexer — which puts us straight back to trusting an operator. Keeping preimages on-chain forever would also be permanently costly and permanently disclosing, where the whole point is a bounded window.

Off the board, on purpose

Paste-ready · 873 · no limit
Escrow, mint/burn and ERC-3643 transfer restrictions: authoritative money and token movement stays on the settlement chain. Arkiv is read after settlement, never in the trade path. Broker routing: the execution hot path stays at the venue. Pre-trade order plaintext: only the commitment goes up before execution — publishing size and side ahead of a fill would manufacture the front-running this exists to detect. The reveal lands post-settlement, when it's stale. Holder portfolios and PII: stay in the issuer's private ledger. Arkiv carries per-order proofs keyed by a pseudonymous wallet — pseudonymity, not privacy, which I flag as a real tradeoff. Broker statements: hash on Arkiv, blob elsewhere. Enforcement: Arkiv answers queries, it runs no triggers — a lapsed attestation or unanswered claim is a state the app reads and acts on, not something the chain enforces.

The weekend slice

Paste-ready · 742 / 800

An Audit view: paste an order id, get a verdict. It reads the OrderSettled commitment from the settlement chain, fetches the matching ExecutionProof entity from Arkiv, recomputes keccak256 over the payload, and renders one of three states — verified, mismatch, or not published — beside the fill price, the oracle benchmark at fill time, and the deviation in bps. That's two entity types (IntentCommitment, ExecutionProof), one write added to the existing settlement listener, and two queries. The first 100 entities are a backfill of paper fills already in the private ledger, so it verifies real fills from minute one. Not in v1: the dispute pair and the cross-issuer board — both add a second party before the single-issuer loop is proven.

No deployment involved

Worth a line in the form: the slice is designed, not deployed. Braga sunset on 12 August and the public testnet arrives in September, so the schema above is offline design against the SDK's shape — which is what the event asks for.

Judges' angles Adoption & the riskiest assumption Not a form field. Fold into the problem or scope answer — the coach's bank probes both.

Who writes the first hundred entities

Single-player from day one: an issuer can publish unilaterally and get value immediately, because verifiable best execution is a claim no competitor can currently make. Every tokenized-equity issuer says fully backed; none of them can be checked. The first hundred entities are mine — a backfill of existing paper fills. The activation event is the first time someone who is not the operator pastes an order id from their own wallet history and watches the hash match.

The second party is where it compounds. Because the schema is shared rather than proprietary, a third party can build a comparison board that ranks issuers on measured deviation instead of marketing copy — and at that point non-publication becomes conspicuous rather than merely unhelpful.

The assumption that would kill it

That an issuer will voluntarily publish evidence which can later be used to prove they gave someone a bad fill. If that is false, the idea as pitched dies.

Reasons it may hold: a new entrant can use transparency as a wedge against incumbents; best-execution reporting is already an obligation on the TradFi leg, so this is a cheaper automatic version of a report the issuer owes anyway; and deviation against a public oracle is a metric an issuer improves by routing better, which makes it a scoreboard rather than a confession.

How to test it without deploying anything: backfill the existing fill history, compute what the outlier report would actually have said, and put that page in front of two or three RWA issuers. If the answer is we would never publish this, the design survives by inverting — a third-party board built only from on-chain commitments and independent oracle data, where the missing preimage is the finding. That fallback needs no issuer cooperation, which is why the riskiest assumption is survivable rather than fatal.

At 100× the data

The outlier report degrades first, if it's allowed an unbounded time range in a shared public database. epochMonth pins every report query to a single month, app and symbol keep filters selective, count() replaces fetch-everything for denominators, and qualityTier bounds the worst-N candidate set. Public readability isn't a leak here — the product is transparency and a scraper is the intended reader. The two things that must not leak are handled above: pre-trade intent stays a hash, and identity stays pseudonymous.

Judges' angles Uniqueness 10 points. The weakest criterion for this idea — worth the paragraph.

Against the obvious version

The nearest obvious submission is Oracle Round Notes with RWA vocabulary: publish price snapshots, let people look at them. Three data-model decisions separate this from that, and they're decisions rather than framing:

  1. The entity is the preimage of a hash that already exists on-chain.

    Verification is a hash recomputation with a binary result, not a reader forming an opinion about a published number. The chain already committed; Arkiv supplies the openable half.

  2. Absence is a designed signal.

    The reserve attestation is kept alive by Lifetime Extension, so a lapse is the disclosure. Most evidence boards treat expiry as cleanup.

  3. The dispute record is an append-only pair with the claimant as $owner.

    The party being accused cannot delete the accusation. Most pitches in this shape quietly assume a mutable status field the platform owns — which, on a full-replace update model, is also the buggier design.

Before you submit Three calls that are yours I've assumed answers where I had to. These are the ones to actually decide.
  • Whether to also enter the Other lane. One idea per track, up to four entries, and Other closes the same day as DeFi. A registry-and-provenance framing of the same domain would be a genuinely different idea, not a resubmission of this one — but it needs its own schema, not this one relabelled.
  • The retention numbers. I used 180 days for the contest window because it is demo-plausible and keeps the intent, proof and response lifetimes coherent. If you have a real regulatory basis for the number, use that instead and say where it comes from — it will read stronger than a round figure.
  • The originality line. The rules ask you to state what's yours when building on prior art. The commitment scheme and the settlement path are yours; commit-reveal and proof-of-reserve are public prior art. Worth one sentence in the form rather than leaving a judge to wonder.
